# Tencent Cloud SaaS foundation

This directory is the D7 Terraform candidate for the isolated JINGTANG SaaS data plane in Tencent Cloud Seoul (`ap-seoul`). It replaces the obsolete AWS CDK scaffold; it does not manage the independently deployed Seoul public website. The website and SaaS are separate resource boundaries even though both are in the same region.

The configuration creates the reviewable foundation only. A production `plan` or `apply`, CIAM/Google Console change, DNS change, secret population, credential rotation, migration, deployment, or rollout is an external write and requires the applicable D7 Production Change Authorization.

## State and credentials

- Configure the `cos` backend bucket, Seoul region, and state prefix from protected CLI/backend configuration. The repository forces private ACL and COS server-side encryption; the pre-created backend bucket must also use versioning, a dedicated least-privilege operator policy, access logging, and a reviewed retention policy. Never commit backend credentials, state, plan files, or `terraform.tfvars`.
- Authenticate the Tencent provider with the protected environment/federation available to the approved operator. The provider block intentionally contains no long-lived credential.
- The CVM receives a non-console CAM role. Application, dispatcher, and worker processes use its rotating STS credentials from instance metadata for only the named private COS objects, the two KMS keys, and CIAM identity deletion; deployed runtime configuration must set `TENCENT_CREDENTIAL_PROVIDER=cvm_role` and must not contain account SecretId/SecretKey values.
- The two password variables are one-use resource bootstrap values required by the Tencent Terraform resources. They are sensitive but necessarily appear in protected Terraform state and possibly saved plan material. Supply them only through the protected operator session, keep state and any authorized plan inside the encrypted/private remote-state boundary, and destroy local plan material immediately after use. After apply, rotate both credentials, seal the active runtime values into the dedicated private COS secret bucket, and never put the rotated values back into Terraform; the one-use values retained in historical state must already be invalid.
- The protected secret-bundle publisher generates a random data key, encrypts the role allow-listed JSON payload with authenticated encryption, wraps the data key with the dedicated runtime-secret KMS key, and writes only the resulting envelope to `platform/runtime.enc`, `dispatcher/runtime.enc`, or `worker/runtime.enc`. Each deployment selects an exact immutable COS version ID. The platform alone receives the CIAM browser OAuth client secret; the worker uses its CAM role and CIAM user-store identifier only for account deletion. The runtime CVM role has read access only to the named bundle objects and decrypt access only to the dedicated key. Active runtime secrets must never enter Terraform state, a container image, Git, ordinary CI/deploy artifacts, logs, screenshots, or shell history; the explicitly documented one-use resource bootstrap exception is confined to encrypted/private Terraform state and is invalidated immediately after provisioning.
- All three private COS buckets inherit their Terraform-managed customer KMS default. Runtime uploads must not replace that default with an object-level AES256 header. Each OAuth connection stores its wrapped data key at one exact versioned object reference; token open and destruction address that same COS version, so a disconnect does not leave a recoverable wrapped-key version behind a delete marker.
- Tencent Cloud International Secrets Manager is intentionally absent: its documented API region list does not currently include `ap-seoul`. Do not add a cross-region SSM dependency. A future managed-secret migration requires verified Seoul availability and an approved Architecture/Security revision.
- The repository supplies the startup loader and the authorization-guarded stdin publisher. `pnpm secrets:publish:tencent` refuses any write without `JINGTANG_PRODUCTION_CHANGE_AUTHORIZED=true` and a change reference; its output contains only object/version identifiers. Publishing or rotating a bundle remains an external write and must not run before the matching D7 Production Change Authorization.
- CIAM application, registration/login flows, auth sources, callback URLs, production Google OAuth client, and reviewer account are control-plane evidence outside the current Tencent Terraform provider surface. Their identifiers enter the runtime secret only after an approved change.

## Regional preflight

- Keep `region = "ap-seoul"`. The current Tencent Cloud zone identifiers are `ap-seoul-1` and `ap-seoul-2`.
- Query the current account's CVM image/SKU, TencentDB engine/SKU, and Managed RabbitMQ numeric zone IDs immediately before plan/apply. The example deliberately leaves `tdmq_zone_ids` empty so it cannot become accidental deployment evidence.
- Confirm the selected CIAM tenant's contractual processing location separately. Terraform validation proves configuration shape only; it does not prove account entitlement, product capacity, data residency, or a deployed control.

## Release candidate boundary

- `Dockerfile` builds one Git-revision-labelled image for the platform, dispatcher, and worker. `Caddy.Dockerfile` builds the ingress from an exact reviewed Caddy source revision with explicitly upgraded security dependencies into a scratch runtime. `compose.yaml` runs the three processes independently behind that release-labelled ingress, uses read-only filesystems, and exposes only ports 80/443.
- Create `/srv/jingtang/saas/runtime.env` from `runtime.env.example` with mode `0600`. It contains identifiers and exact encrypted-object version IDs only; `activate-release.sh` rejects known plaintext-secret names.
- Before first application activation, a protected database operator creates separate `jingtang_app` and `jingtang_worker` login roles, runs the canonical forward-only migrations with the administrator connection, rotates the runtime credentials, and publishes the three sealed bundles. The administrator URL/password is never put in a runtime bundle or image.
- The protected `production-saas` workflow reruns `pnpm verify`, builds amd64 application and ingress images labelled with the exact Git SHA, blocks on High/Critical vulnerability findings for both, checks both transferred archive checksums and image labels, and invokes the host activation script. Defining this workflow does not authorize running it.
- The CVM image must already be patched and include Docker Engine, Docker Compose v2, the Tencent CLS LogListener, time synchronization, and the approved host hardening. Capture those controls, the actual capacity/zone inventory, and alert routing as protected D7 evidence before rollout.

## Validation

Run `pnpm infra:validate`. It initializes providers without the production backend, executes official `terraform validate`, and enforces official formatting. A passing local validation is not production evidence and does not authorize `plan` or `apply`.
